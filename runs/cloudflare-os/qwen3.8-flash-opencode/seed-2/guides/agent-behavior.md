# How to Change Agent Behavior

Mechanics are in [Agent Runtime and Tools](../backend/agent-runtime.md); this page is "I want the agent to do X differently — what do I touch, and what breaks?"

## The system prompt and tool descriptions (`agent.ts`)

The prompt is a plain string region of `packages/workshop-backend/src/agent.ts` (~L570 onward: workspace model, blueprint-first rule, gadget authoring contracts, `describeBinding`-before-`executeCode` discipline) and each tool's description is its own `*_TOOL_DESCRIPTION` constant feeding the `tools` map (agent.ts#L570-L870, #L2302-L2856). The model's behavior *is* this text plus the tool schemas — changing it changes every deployment's agent, so review it like kernel code. Conventions encoded there that callers depend on:

- "Users rarely ask for 'a Gadget' in those words… any of those is a request for a new Gadget, and so a request to consider a blueprint" (the blueprint-first default) (agent.ts#L574-L576).
- Bindings "most likely do NOT implement any API you are familiar with" — discovery must go through `describeBinding`, never guessed or enumerated (agent.ts#L840-L850).
- Gadget code cannot network; `webFetch` is the agent's tool, not the gadget's (agent.ts#L815).

To **change what tools exist**: edit the `tools` map — but note the two deliberate sub-surfaces: callback-initiated runs add `giveUp` (agent.ts#L2859-L2873), and spawner-created sub-agent chats are *restricted* to `describeBinding`+`executeCode`(+`giveUp`) (agent.ts#L2877-L2883). Widening one path silently widens blast radius of spawned agents; the tool-call argument validation for these is generated by `@validateRpc` on the server classes, so schema changes ride automatically (see [How to Change the RPC API](changing-the-rpc-api.md)).

## Per-deployment instructions (soft config, admin panel)

`AdminConfig.instanceInstructions` is "Extra instructions appended to the agent system prompt" (packages/workshop-backend/src/admin-config.ts#L28-L29). At prompt-build time the agent wraps it via `formatInstanceInstructions` in a clearly delimited block: *"The administrator of this deployment has provided the following additional instructions. Follow them unless they conflict with the user's safety or the instructions above."* inside `<deployment_instructions>` tags (packages/workshop-backend/src/admin-config.ts#L345-L357; consumed at packages/workshop-backend/src/agent.ts#L2056). It is deployment-scoped *soft* config: owned by the AdminSettings DO (sole writer), mirrored to reserved KV for one-get hot reads, edited through the admin panel — no deploy needed (see [Admin Settings and Configuration](../operations/admin-and-configuration.md)). The precedence line is the security-relevant part: admin text can extend, not override, the built-in prompt or user safety.

Related soft knobs that steer behavior: promoted output formats carry an `agentHint` that goes into the prompt ("what the agent is told to prefer", length-capped) (admin-config.ts#L49-L56, #L97-L99), and disabled resources/vendors change what the agent can even request (the `getGatekeeperClassFor` chokepoint, [Gatekeeper Framework](../gatekeepers/framework.md)).

## Budgets and compaction: correctness constants, not tuning knobs

Before changing any of these, read the rationale comments — each exists to make a failure mode impossible, not to save tokens:

- `CHAT_CHANGE_MESSAGE_BUDGET` / `STEP_CHANGE_BUDGET` in agent.ts#L34-L65: bounding accumulation and per-step writes against the 2 MB DO storage-record cap. The comments explain why *composition* is bounded by summing rows (`codeChangeSerializedSize` never exceeds the sum of inputs) and why a step over budget fails the offending tool call while keeping prior edits — so mid-turn model adaptation works. A known accepted gap (multi-file `createGadget` blueprint copies) is documented at agent.ts#L57-L61.
- `MAX_FILE_TEXT_LENGTH`, `MAX_FILE_PATH_LENGTH`, `MAX_CODE_CHANGE_SIZE` in packages/workshop-shared/src/code-change.ts#L126-L144 — shared with the frontend OT client and validated server-side; changing one side's bound alone just moves where rejections land.
- Compaction: `COMPACTION_TRIGGER_RATIO = 0.85` of the model's input budget starts compaction; `COMPACTION_TARGET_RATIO = 0.3` sizes the retained tail (packages/workshop-backend/src/agent-compaction.ts#L13-L17, #L58-L59, #L323). The summarizing turn's own prompt is `COMPACTION_SYSTEM_PROMPT` (agent-compaction.ts#L43-L45) — it exists so "the same coding agent [can] continue this conversation," preserving requirements, decisions, files, errors, and next steps; edits should keep the *handoff* framing, and boundary selection must keep protecting reverts (`findProtectedFromSequence`/`protectRetainedReverts`) or users lose the ability to roll back across a compaction.
- Model token limits come per-config from `getModelTokenLimits` (agent-compaction.ts#L28), so the budget a new provider model gets is derived from its declared context, not a constant.

## Model and provider surface

What models exist at all is configuration, not prompt: users pick from per-user model profiles (`AuthenticatedApi.addModel`/`listModels`, packages/workshop-frontend/src/AddModelModal.tsx; suggestions in packages/workshop-shared/src/api.ts#L1186), while platform routing depends on env — `CF_AI_GATEWAY` (+`CF_AI_GATEWAY_ACCOUNT_ID`, token vs Workers-AI binding modes) enables gateway-funded inference, and its absence means direct provider calls with user-supplied tokens (packages/workshop-backend/src/ai-gateway.ts#L12-L54). BYOK via a connected Cloudflare account overrides routing for billing correctness (packages/workshop-backend/src/ai-models.ts#L356-L379), and the optional daily-allowance mode is `ENABLE_CLOUDFLARE_LIMITS` (docs/ai-gateway-billing.md). To "make the agent better at X," prefer: better prompt/tool-description text, promoted-format `agentHint`s, or admin instructions — before touching budgets, which are load-bearing.

## Verify a behavior change

`run-local`/`dev-server`, then drive a chat: watch `executeCode` env contents (ambient capsule presence/order, [Agent Runtime](../backend/agent-runtime.md)), the action log's observation entries (each read must appear — absence means an unaudited path), and compaction by running a chat long past the trigger. The agent-relevant suites: `pnpm --filter @gadgets/workshop-backend test:run` (chat/compaction unit tests live beside the frontend's `ChatInterface.compaction.test.ts` for the UI side), and integration suites for gatekeeper-facing flows (packages/workshop-frontend/src/ChatInterface.compaction.test.ts; [Testing Approach](../development/testing.md)).
