# Persistence and Blueprints

## typed-storage: the DO storage layer

`@gadgets/typed-storage` gives Durable Objects a schema layer over their SQL storage:
`createTypedStorage(ctx.storage, {collections, singletons})` builds collections with a primary key
plus unique/non-unique indexes, all transactions run through `transactionSync`, and singletons
serve as defaulting KV slots with subscribers (packages/typed-storage/src/index.ts#L668-L700).
Key `list()` semantics are documented as footguns-on-purpose: for non-unique indexes `limit`
counts matching keys rather than records (so more than `limit` records may return, while
`startAfter` from the last key never misses anything), and `dedupe` interacts badly with `limit`
across paginated calls (packages/typed-storage/src/index.ts#L29-L54). It is the one workspace
package that emits compiled JS because its `exports` resolve to `dist/index.js`
(packages/typed-storage/package.json#L5-L15).

Collections and their keying are declared per DO — e.g. chat messages keyed
`{chatId}.{sequence}` in the overseer (packages/workshop-backend/src/overseer.ts#L1183) and the
git objects collection keyed by object id (packages/workshop-backend/src/git-store.ts#L60-L69,
explained at L23-L28: loose objects only, one record per zlib'd object, dedup by content
addressing, no GC).

## KV and R2

The backend worker binds two KV namespaces (`BLUEPRINTS`, `AVATARS`) and one R2 bucket
(`BLUEPRINT_CONTENT`), plus the `BROWSER` and `LOADER` bindings
(packages/workshop-backend/wrangler.jsonc#L64-L86). Blueprint *metadata* lives in KV keyed by
blueprint id; blueprint *code content* and *screenshots* live in R2 — screenshot objects are keyed
under the `screenshots/` prefix and served at `/blueprint-screenshot/<id>` by
`blueprintScreenshotUrl()` (packages/workshop-shared/src/api.ts#L3700-L3710,
packages/router/src/index.ts#L36-L39). The KV namespace also holds two *reserved* keys,
`.featured` and `.adminConfig`, which `isReservedBlueprintKey()` shields from being used as
blueprint ids (packages/workshop-backend/src/blueprint-archive.ts#L10-L16, L37-L39);
`.adminConfig` is the AdminSettings DO's mirror read by hot paths
(see [Configuration](../operations/configuration-and-admin.md)).

## Blueprints: three stores, one-way propagation

Blueprint state flows one way — **Gadget DO → User DO → Workers KV**
(docs/blueprints.md#L48-L60):

1. The gadget's `blueprints` collection is authoritative and carries a `dirty` flag to track
   propagation failures.
2. The user DO keeps a denormalized copy for listing/audit, surviving deletion of the source
   gadget.
3. KV holds the public-facing `BlueprintKvRecord` (`metadata` + optional `ownerId`/`gadgetId`)
   that `PublicApi.getBlueprint()` reads without authentication — knowing the 128-bit random hex
   id (generated by `randomBlueprintId()` via `crypto.getRandomValues`) is the access grant
   (packages/workshop-backend/src/blueprint-archive.ts#L26-L35, L143-L147,
   packages/workshop-shared/src/api.ts#L120-L133).

A blueprint captures committed code (a history-stripped Yjs snapshot), binding *shapes* with
optional author annotations, and metadata — never SQLite contents, chat history, or credentials
(docs/blueprints.md#L21-L46). Old code versions are retained in storage so concurrent
instantiations can't race the author updating a version, and instantiating creates a fresh
Overseer DO from KV metadata + R2 code
(packages/workshop-shared/src/api.ts#L645-L655, docs/blueprints.md#L17-L19).

Bundled *format* blueprints ship in the deployment as data — a `<name>.gadget` archive plus a
`<name>.json` sidecar whose curated fields (including `blueprintId`) overwrite whatever the
archive carries — installed into KV/R2 by the first `/api` request
(packages/workshop-backend/format-blueprints/README.md#L1-L24; trigger in
packages/workshop-backend/src/server.ts#L816-L845). The `blueprintId` is the install key —
changing it after a deployment installed it leaves the old entry orphaned in the New menu — so it
must never be edited post-deploy (packages/workshop-backend/format-blueprints/README.md#L76-L82;
see [How to Add a Format Blueprint](../guides/adding-a-format-blueprint.md)).

## The `.gadget` archive format

Archives are streamed as a 24-byte prefix — 8-byte magic `0xec2e2d3a2300e317`, 4-byte version,
4-byte metadata length, 8-byte content length — followed by UTF-8 JSON metadata and a
gzip-compressed Yjs snapshot, parsed with caps of 64 KiB metadata / 32 MiB content
(packages/workshop-backend/src/blueprint-archive.ts#L1-L19, L149-L160, L161-L255, L256+).
Untrusted metadata is *sanitized* rather than trusted: `sanitizeBlueprintOutput()` drops a
blueprint's declared output format entirely unless every field (including the icon key) is
well-formed, so a hostile upload degrades to "generic app" instead of breaking the UI
(packages/workshop-backend/src/blueprint-archive.ts#L48-L72).

## Sharing: lazy revocation in a permission graph

`SharingManager` owns the `collaborators` and `shareKeys` collections plus the permission graph,
and deliberately performs no RPC (the overseer passes resolved values in)
(packages/workshop-backend/src/sharing.ts#L1-L9). The model is **lazy revocation**: effective
access is reachability from the owner, recomputed at every `open()`; revoking a collaborator
severs only their edges and revoking a link only flags it — nothing cascades or deletes, so
re-adding a user transitively restores everyone downstream, and dead records accumulate for a
future GC (packages/workshop-backend/src/sharing.ts#L11-L19). Roles are totally ordered
(`build` > `use`, with pre-role records defaulting to `build`), and share-link keys are hashed with
a fixed domain-separation HMAC key (not a secret) (packages/workshop-backend/src/sharing.ts#L26-L50).
The broader `prohibitAllSharing` policy flag is enforced by the overseer, not here
(packages/workshop-backend/src/sharing.ts#L20-L23). Observer enforcement on top of sharing is
covered in [Capability Security Model](../security/capability-security-model.md).

## Export bounds

All streaming exports share two constants — a 30 s wall-clock deadline (`createExportDeadline`,
raced against delivery) and a 100 MiB byte cap
(packages/workshop-backend/src/export-limits.ts#L1-L28) — applied to both server- and
browser-mode gadget exports (packages/workshop-backend/src/gadget-export.ts#L1-L5).
