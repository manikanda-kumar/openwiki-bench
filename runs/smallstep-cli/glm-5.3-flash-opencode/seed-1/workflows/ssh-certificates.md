# SSH Certificates

## Scope

The `step ssh` group issues and manages SSH user and host certificates signed
by a step-ca (online or offline). It shares the token system with X.509 flows:
SSH sign tokens are generated by `CertificateFlow.GenerateSSHToken` /
`SignSSHToken` using the same provisioner dispatch, with the SSH audience
(`/1.0/ssh/sign`, `/1.0/ssh/renew`, `/1.0/ssh/rekey`, `/1.0/ssh/revoke`)
(repo://command/ssh/ssh.go, repo://utils/cautils/token_generator.go#L124-L140,
repo://utils/cautils/token_flow.go#L59-L66).

## Issuance: step ssh certificate and login

- `step ssh certificate <identity> <cert-file> <key-file>` creates a key pair
  and requests a user or host certificate (`--host` flag), with principals,
  validity windows, and template data (repo://command/ssh/certificate.go).
- `step ssh login [<identity>]` generates a key pair, requests a **user**
  certificate, and adds it to the SSH agent. It requires a running agent
  (`sshutil.DialAgent`). Unless `--force`, it first checks the agent for a
  still-valid certificate signed by the CA (filtered by the CA's user keys as
  signature keys and `WithRemoveExpiredCerts(now)`) and returns early when
  present. `abc@def` identities become the `abc` principal
  (repo://command/ssh/login.go#L119-L190).
- `step ssh logout` removes certificates from the agent by comment/signer
  (`sshutil.Agent.RemoveKeys` / `RemoveAllKeys`) (repo://command/ssh/logout.go,
  repo://internal/sshutil/agent.go#L201-L243).

## Agent integration

`internal/sshutil/agent.go` wraps `golang.org/x/crypto/ssh/agent` with
filtering options: `WithSignatureKey(keys)` (only keys signed by the given CA
public keys), `WithCertsOnly`, and `WithRemoveExpiredCerts(t)`; it can list
certificates, get a key/signed by comment, and add certificates with their
private key (repo://internal/sshutil/agent.go#L32-L258). Transport is
platform-specific: `pipe.go` resolves the named pipe on Windows (including
reading a configured pipe name from an sshd config) and falls back to
`SSH_AUTH_SOCK` elsewhere (repo://internal/sshutil/pipe.go#L16-L40).

## Single sign-on: proxycommand

`step ssh proxycommand <user> <host> <port>` is designed to be installed as an
`ProxyCommand` in the ssh client config. It (repo://command/ssh/proxycommand.go#L70-L97):

1. Calls `doLoginIfNeeded` — inspects the agent for a valid user certificate
   signed by the CA and, if missing, runs the login flow (automatic SSO);
2. Asks the CA for a bastion configuration (`getBastion` → `SSHBastion` API);
3. Either connects directly to the target or proxies through the bastion,
   rendering the bastion's command template via `sshutil.ProxyCommand`
   (repo://command/ssh/proxycommand.go#L100-L218, repo://internal/sshutil/shell.go#L25-L34).

`internal/sshutil/shell.go` also provides the interactive shell used by
`step ssh <host>`-style flows: certificate-based auth, remote command
execution, and local port forwarding (repo://internal/sshutil/shell.go#L111-L246).

## SSHPOP lifecycle operations

Renew, rekey, and revoke of SSH certificates authenticate with the **SSHPOP
provisioner**: the existing SSH certificate and its private key are embedded in
the token (`WithSSHPOPFile`) and the audience targets the SSH lifecycle
endpoints (repo://utils/cautils/token_generator.go#L313-L345). Offline mode
implements these through the embedded authority (`SSHRenew` extracts the
SSHPOP cert from the token, `SSHRekey` signs a new cert for a supplied public
key) (repo://utils/cautils/offline.go#L397-L440).

## Hosts, known-hosts, and config templates

- `step ssh hosts` lists hosts known to the CA (`SSHGetHosts`);
  `step ssh check-host <principal>` asks whether a host principal exists
  (`SSHCheckHost`) (repo://utils/cautils/client.go#L42-L43).
- `step ssh config` writes SSH client/server configuration snippets and
  known-host entries derived from the CA's templates (`SSHConfig` API returns
  user/host templates; the offline implementation maps both to UserTemplates)
  (repo://command/ssh/config.go, repo://utils/cautils/offline.go#L480-L499).
- `step ssh inspect` prints certificate details using `internal/sshutil`'s
  certificate parsing (`ParseCertificate`) and public-key type/size
  introspection (repo://command/ssh/inspect.go, repo://internal/sshutil/sshutil.go#L22-L67).

## Invariants and failure behavior

- `step ssh login` fails fast without an agent (`DialAgent` error), and its
  early-return path depends on the CA's user roots being fetchable; if
  `SSHRoots` fails it simply skips the signature-key filter (repo://command/ssh/login.go#L160-L190).
- The proxycommand always requires exactly three arguments and treats a missing
  bastion as a direct connection (repo://command/ssh/proxycommand.go#L70-L97).
- SSH token generation reuses the provisioner prompt/filter machinery from the
  X.509 flow, including the same typed errors for ACME/SCEP provisioners
  (repo://utils/cautils/token_flow.go#L154-L183).

## Uncertainty

The `--add-user` flag on `step ssh login` suggests user-provisioning behavior
on the remote host; the remote-side semantics depend on CA templates and are
not established by this repository (repo://command/ssh/login.go#L150).
